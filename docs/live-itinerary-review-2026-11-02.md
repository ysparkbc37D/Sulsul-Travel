# 여행 중 자유 편집을 위한 현행 검토와 개선 설계

2026-11-02 · 검토 기준 v1.9.6 / `fd827a0`. 이 문서는 수정 전 재현과 제안이다. 아래는 당시 수정 전 설계다. 이후 직접 편집·기준안·이력의 구현 범위와 남은 과제는 [v1.9.7 구현](live-itinerary-v1.9.7.md)에서 구분한다. 사용자 여행·사진·키는 재현 자료로 사용하지 않았다.

## 판단

사용자의 지적에 동의한다. v1.9.6에는 추가·수정·취소·대체·삭제 버튼과 저장 경계가 있지만, 여행자가 원하는 위치에 일정을 끼워 넣고 순서·날짜를 바꾸는 편집기가 되지는 못했다. 이전 검사의 개별 저장 성공을 실제 장기 여행의 편집 완성도로 해석한 것은 잘못이었다.

개선 목표는 **처음 만든 계획을 참고하면서 현재 실행할 여행을 자유롭게 편집하고, 실제로 한 일은 별도 기록으로 남기는 것**이다. 재생성이나 시각 일괄 이동을 거치지 않아도 직접 편집이 완결되어야 한다.

## 실제 확인한 결함과 제한

격리된 Edge Chromium, 390×844 화면, 합성 2일 여행에서 실제 ‘일정 추가’ 폼을 사용했다. 실행 재현은 `.local-review/live-itinerary-audit-2026-11-02.cjs`, 결과는 같은 이름의 JSON에 보관했다. 두 파일은 공개 배포 대상이 아니다.

| 우선순위 | 현재 동작/원인 | 재현 또는 코드 근거 |
| --- | --- | --- |
| P0 | 시간 범위를 잘못 해석하여 삽입 순서가 틀림 | `index.html`의 `timeToMinutes`가 `09:30~10:00`을 570분 대신 540분으로 계산. 09:00 A → 09:30~10:00 B에 09:15 N을 추가하면 A→B→N으로 저장됨 |
| P0 | 자정 범위의 시작 날짜까지 잘못 변경 | `23:30~+1일 00:30`을 시작 1410분 대신 2820분으로 계산. 문자열 어디든 `+1일`이 있으면 시작에도 하루를 더함 |
| P0 | 다른 날짜에 불필요한 변경을 일으킴 | `submitSpot`이 모든 day를 강제 시간 정렬. 첫날 삽입만 해도 둘째 날 [D 14:00, E 13:00] 순서가 [E, D]로 변경됨 |
| P1 | 추가 위치를 지정할 수 없음 | `openAddSpotToDay`는 날짜만 선택하고 `submitSpot`은 배열 끝에 push한 뒤 시간 정렬. 카드 앞/뒤·현재 위치·선택한 지점 사이의 삽입 계약이 없음 |
| P1 | 시간을 모르면 신규 방문을 만들기 어려움 | 추가 폼의 기본값은 09:00. 시간을 비우면 저장 거절. 현장 방문을 우선 추가하고 나중에 시각을 정하는 흐름이 없음 |
| P1 | 순서 변경과 시간 변경이 결합됨 | 별도 사용자 지정 순서 필드/명령이 없고 저장 시 시간 정렬이 순서를 결정. 같은 시각·겹치는 예약·시간 미정의 의도를 표현하기 어려움 |
| P1 | 복구와 되돌리기가 부분적 | 취소는 복구하지만 삭제는 `splice`로 제거. 삽입·이동·수정·대체의 변경 이력과 Undo 명령은 없음 |
| P1 | 큰 계획·기록·실행의 기준이 혼합됨 | `trip.days`를 생성·수정·AI 재계획·날짜 편집이 함께 변경. 최초 확정 계획의 독립 스냅샷과 실제 시작/종료의 공통 모델이 없음 |
| P1 | 기록 보호가 미래 계획 수정까지 묶임 | AI 검증과 지연은 `recordId`가 있으면 일정 전체를 보호. 방문 전 메모만 쓴 항목과 실제 완료 방문을 구별하지 못함 |
| P1 | 화면 갱신이 분산됨 | `refreshScheduleViews`가 시간표·큰 계획·오늘·상세를 각각 재생성. 지도·요약 등은 별도 경로. 한 계획의 동일한 변경 상태를 일관되게 투영하는 경계가 부족함 |
| P2 | 장기 여행 편집 비용이 커짐 | 한 항목 수정에도 모든 여행 JSON 복사·직렬화와 숨은 전체 시간표 렌더링을 수행. 휴대폰 성능 수치는 이번에 측정하지 않았으나 전체 순회는 코드로 확인 |
| P2 | AI의 전체 문서 계약이 긴 여행과 삽입에 부적합 | `AiDraftValidation`은 최대 60일·하루 48항목, RePlan은 기존 일수와 날짜 배열 순서를 유지하도록 검사. 날짜 삽입·긴 여행의 일부 편집을 전체 재생성에 맡기기 어려움 |

실제로 가능한 것도 구분한다. 기존 폼에서 날짜를 골라 일정 하나를 다른 날로 옮길 수 있고, 수동 수정·취소·대체·삭제도 가능하다. 문제는 이 기능들이 빠른 연속 편집과 일관된 순서·화면·기록 관리로 연결되지 않는다는 점이다.

## 다른 앱에서 확인한 기준

- [Wanderlog 공식 이동 안내](https://help.wanderlog.com/hc/en-us/articles/5159751100443-Move-a-place)는 장소 순서 드래그와 선택한 날짜로 이동을 별도 동작으로 제공한다. 술술에는 ‘시각을 바꾸지 않는 순서 이동’과 ‘다른 날짜로 이동’을 명시적으로 제공하는 근거로 삼는다.
- [TripIt 공식 편집 안내](https://help.tripit.com/en/support/solutions/articles/103000063279-edit-trip-itinerary-in-the-tripit-website)는 여행 전체 정보와 개별 계획의 편집·삭제·추가를 구분한다. 큰 계획 편집창을 거치지 않고 일정 항목 자체를 다룰 수 있어야 한다.
- [Tripsy 공식 소개](https://tripsy.app/)는 편집 동행자와 보기 전용 권한, 문서·지출 접근을 구별한다. 이를 술술의 개인 기록과 공동 계획의 권한 분리에 참고한다. 이 소개만으로 동시 편집 충돌 해결 방식이나 술술과의 기술 연동이 검증된 것은 아니다.

위는 공식 화면 설명을 확인한 사실이다. 아래의 삽입 버튼·대기함·Undo·3계층 구조는 술술의 컨셉에 맞춘 제안이며, 비교 앱이 모두 같은 방식으로 구현했다는 뜻이 아니다.

## 제안하는 휴대폰 편집 흐름

주 화면은 ‘현재 여행의 오늘’이다. 상단에 날짜와 저장 상태, `+ 추가`, `순서 편집`, 사용 가능한 `되돌리기`를 둔다. 큰 계획은 도시·숙소·예약 등 여행의 뼈대를 확인하는 진입점으로 유지한다.

| 여행 중 의도 | 제안 동작 | 시간·기록 처리 |
| --- | --- | --- |
| 두 장소 사이 약국에 잠깐 들르기 | 카드 사이 `여기에 추가` → 제목/장소와 예상 소요만 입력 | 선택한 위치에 삽입. 정확한 시각은 선택 사항 |
| 지금 보이는 다음 일정 앞에 넣기 | 카드 메뉴 `앞에 삽입` / `뒤에 삽입` | 선택한 카드 ID를 기준으로 위치 지정 |
| 순서 바꾸기 | `순서 편집`에서 손잡이 드래그, 위·아래 이동 버튼도 제공 | 기본은 시간 유지. 충돌은 표시하고 후속 재계산은 별도 선택 |
| 박물관을 내일 오후로 미루기 | `다른 날짜로 이동` → 날짜·삽입 위치 지정 | 동일 일정 ID 유지. 오늘/내일·큰 계획·지도 함께 갱신 |
| 방문 여부를 아직 못 정함 | `나중에 갈 곳`으로 보내기 | 예정 경로에서 빼고 대기함에 보관. 취소·삭제와 구별 |
| 일정을 빼기 | `일정에서 제거` → 저장 후 `되돌리기` | 보관 상태로 전환하고 계획 이력 유지. 글·사진을 지우지 않음 |
| 박물관 대신 30분 카페 가기 | `대체` → 직접 선택하거나 AI 후보 검토 | 원래 항목의 상태·대체 관계 보존, 새 방문에 새 ID |
| 계획에 없던 곳을 이미 방문함 | `방문한 일 추가` | 처음부터 실제 기록으로 입력. 날짜·시각은 사용자가 확인 |
| 삭제나 이동을 실수함 | 하단 Undo 또는 변경 이력 | 대상이 이후 바뀌었으면 충돌 안내. 다른 사람 수정까지 되감지 않음 |

빠른 추가의 필수값은 활동명 하나로 시작한다. 장소·소요·시각·비용·메모는 펼쳐서 보완한다. 빈 임시 카드를 확정 데이터로 저장하지 않으며, 입력 중 초안과 저장 실패는 별도로 보존한다.

이동·삭제·삽입을 수행할 때 매번 큰 계획·AI 창을 왕복하지 않는다. 같은 날짜, 선택 카드, 스크롤 위치를 유지한다. 스와이프만으로 영구 삭제하지 않고, 드래그를 못 쓰는 사용자도 버튼으로 모든 동작을 할 수 있어야 한다.

## 계획과 기록의 구조

| 계층 | 책임 | 변경 규칙 |
| --- | --- | --- |
| 처음 확정한 계획 | 출발 전 기준안과 예약 의도 | 비교용 스냅샷으로 보존. 명시적으로 새 기준을 만들 수 있음 |
| 현재 실행할 계획 | 여행 중 추가·이동·보류·대체를 반영한 목록 | 사용자가 자유롭게 편집. 오늘·큰 계획·지도는 이것을 참조 |
| 실제 여행 기록 | 실제 방문, 시각, 글·사진, 원문·승인문 | 계획을 옮기거나 지워도 당시 날짜·문맥 유지 |

기존 `trip.days`를 곧바로 버릴 필요는 없다. 우선 현재 계획의 호환 원본으로 두고 안정 `dayId`/`spotId`, 사용자 순서, 시각 제약과 소요 시간, 상태를 분리한다. 시간 라벨 문자열은 표시/구버전 호환에만 사용하고 비교·연산은 공통 시간 함수로 통일한다.

최소 추가 모델의 예:

```text
item: id, dayId, orderKey, status, start?, end?, durationMinutes?, timeZone
      timeConstraint(flexible/window/reservation), baselineItemId?, replacesItemId?
trip: planRevision, baseline?, scheduleChanges[]
record: 기존 안정 ID와 발생 날짜·원문·사진 연결 유지
```

`orderKey`와 시각을 독립시킨다. 시각 정렬은 사용자가 요청한 명령으로만 한다. 입력한 09:00이 단순 희망 시각인지 예약 고정인지도 구분한다. 방문 전 메모가 있다고 전체 계획을 동결하지 말고 기록 원문과 예정 계획 필드의 보호를 분리한다.

기존 여행의 출발 전 원본은 자동 복원할 수 없다. 이전 자료는 현재 순서·날짜를 유지한 채 채택하고, 기준 스냅샷을 만들면 ‘업데이트 이후 현재 계획 기준’이라고 표시한다. 취소·건너뜀·완료와 기록을 생성된 일반 초안으로 바꾸지 않는다.

## 구현 경계와 AI

`InsertItem`, `MoveItem`, `UpdateItem`, `RemoveItem`, `RestoreItem`, `ReplaceItem`, `RecordVisit` 명령을 한 편집 경계로 모은다. 명령은 날짜/일정의 안정 ID, 삽입 기준 ID와 앞·뒤 위치, 기대 버전, 영향 범위를 받는다. 레거시 화면 함수는 이 명령을 호출하도록 점진적으로 바꾼다.

1. 현재 버전과 권한 확인 → 복사본에 명령 적용 → 영향 범위/기록 관계 검증 → 저장 성공 → 화면에 채택.
2. 날짜 이동은 출발·도착 목록과 변경 이력을 함께 저장한다. 다른 날짜를 자동 정렬하지 않는다.
3. 같은 현재 계획 selector를 오늘·큰 계획·지도·통계·동행 비교·PDF에 적용한다. 제거 상태와 개인 기록 포함 여부는 각 출력의 명시 옵션으로 처리한다.
4. 저장 후 변경 이벤트에서 영향받은 날짜·카드만 갱신한다. DOM 재생성과 스크롤 복귀를 기능마다 구현하지 않는다.
5. 변경 이력에는 변경한 필드와 ID를 남긴다. Undo용으로 모든 여행·사진 원본을 매번 복제하지 않는다. 복구 시 이후 수정 충돌을 검사한다.

현재의 전체 JSON 원문 비교/여행 revision은 데이터 유실을 막는 경계로 유지한다. `planRevision` 필드만 추가해도 원자적 동시 저장이 생기는 것은 아니다. 이후 항목/날짜별 revision, IndexedDB 트랜잭션과 검증된 마이그레이션으로 저장 단위를 줄인다. 원본 백업·비교·실패 복구 없이 저장소를 한 번에 교체하지 않는다.

AI의 역할은 ‘현재 위치에서 남은 2시간으로 갈 수 있는 후보’, ‘선택한 세 일정 재배치’, ‘다음 예약 전 짧은 대체’다. 요청 범위의 추가·이동·제거 제안과 영향을 구조화해 검토한 뒤 동일 명령 경계로 적용한다. 네트워크 실패를 단순 전체 시간 이동으로 조용히 대체하지 않는다. 완료 방문·기록·예약 보호는 유지하되 사용자의 명시적 계획 수정은 별도 경로로 허용한다. 60일을 넘는 여행도 필요한 하루/구간만 보낸다.

실제 교통 소요·영업·티켓 취소는 검증된 공급자 연동이 필요하다. 그런 연동 없이 확정값처럼 제시하지 않는다. 기본 편집은 오프라인에서도 동작해야 하며, 동행자는 명시된 공유 계획과 권한 범위에서만 변경을 받는다. 개인 일기·사진을 계획 동기화에 자동 포함하지 않는다.

## 개발 순서와 통과 기준

| 단계 | 범위 | 완료 판단 |
