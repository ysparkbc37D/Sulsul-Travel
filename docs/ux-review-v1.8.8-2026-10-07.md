# 술술트래블 v1.8.8 모바일 UI/UX 검토

검토일: **2026-10-07** · 기준: `main` / `73aeb0b4d9cc3cba8c656049b5c6c7b2be4466cd` · 상태: 검토 및 개선 설계

## 1. 판단

술술트래블의 중심은 **함께 계획하고, 현장에서 조정하며, 순간을 남겨 평생 다시 읽는 여행 다이어리**다. 현재 구현은 큰 계획 편집, 구간 AI 재생성, 일정별 기록, 지출, 여행 결과 출력까지 갖췄다. 다음 개편은 이 기능들을 여행 단계에 맞게 연결하고, 휴대폰 첫 화면에서 다음 행동을 쉽게 찾도록 만드는 데 집중해야 한다.

크림색·짙은 녹색·여행 노트 분위기는 유지할 수 있다. 필요한 변화는 **화면의 정보 우선순위, 읽을 수 있는 글자색, 충분한 터치 영역, 시간순 기록 구조**다. 특히 최신 기본 여행에서 일정 제목 누락과 사본 내보내기 실패가 재현됐으므로, 콘텐츠 데이터 계약을 먼저 바로잡아야 한다.

권장 순서는 **일정 데이터 복구 → 모바일 화면 정비 → 여러 순간 기록과 사진 보관 → 시간순 에세이 출력 → 동행 공동편집**이다. 기존 PWA와 AI 초안 승인 구조를 유지하면서 단계별로 적용한다.

### UX-01: 최신 샘플의 일정 계약 불일치

원본 일정 제목은 정상이다. [변환 함수](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/kb-travel.js#L434)는 `name: tl.title`을 만들고, [기본 시드](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/index.html#L6572)는 이 결과를 사용한다. 그러나 [카드](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/js/presentation/companion-ui.js#L84), [사본 검증](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/js/domain/trip-transfer.js#L26), [PDF](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/index.html#L19598)는 `title`을 읽는다. 다음 일정 카드의 [fallback](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/js/presentation/companion-ui.js#L137)도 제목 누락을 하루 마무리 문구로 표현한다.

같은 변환에는 `category/cat`, `day/dayNum`, 한글 날짜/ISO 날짜 차이도 있다. 제목과 내보내기 장애는 실제 재현했고, 나머지는 adapter 검증 범위에 넣어야 할 코드 계약 차이다. 화면마다 `name || title`을 덧붙이는 방식보다 입력 경계에서 표준 형태를 만드는 것이 적절하다.

재현 절차: 새 origin에서 앱 실행 → 기본 남미 여행 열기 → 오늘 DAY1 제목 확인 → 공유 → 여행 파일 보내기/내려받기 → 오류 문구 확인.

### UX-02: 도시명 손실

[도시 정리 함수](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/index.html#L6271)가 공백 뒤를 버린다. [목적지 정규화](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/index.html#L6290)가 이 함수를 도시 목록·날짜별 도시에 적용하고, 시작 시 정규화한 여행을 저장하는 경로가 있다. 원본 기본 여행에는 [전체 지명](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/kb-travel.js#L474)이 들어 있다.

`엘`이라는 결과만으로 원래 지명을 확정할 수 없으므로 임의 복원하지 않는다. 구간 메타·날짜별 원본 등 근거가 남은 항목에 한해 복구안을 미리 보여주고 적용해야 한다. 영어의 New York, Buenos Aires도 같은 규칙의 검증 사례에 포함한다.

### UX-03~06: 모바일 가독성과 첫 행동

현재 390px 검토 화면에서 문서 전체의 가로 넘침은 없었다. 남은 불편은 작은 터치 영역과 큰 세로 점유량이다. [HTML 헤더](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/index.html#L1434)에 `.companion-app-header`가 없으므로 [관련 최소 크기 규칙](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/css/companion.css#L79)이 적용되지 않는다. [탭 전환](https://github.com/ysparkbc37D/Sulsul-Travel/blob/73aeb0b/index.html#L10474)은 구간 상세의 복귀 기능과 달리 현재 위치를 초기화한다.

모던 테마의 실제 계산 스타일은 보조 글자 `#8A7868`, 카드 `#FFFDF9`, 페이지 배경 `#F5EFEB`였다. 이 조합의 대비는 각각 4.161, 3.710이다. 이는 측정한 보조 글자 조합의 결과이며 모든 테마/배지의 판정은 아니다. 일반 작은 글자는 **4.5:1 이상**으로 확인한다. [W3C 텍스트 대비 기준](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

보조 글자 후보 `#6F5E4E`는 페이지 배경 5.44:1, 카드 6.10:1, 보조 바탕 `#EDE5DA` 4.97:1이다. 실제 도입 시 상속·반투명 배경·선택 상태까지 검사한다. 44×44px는 술술의 조작 목표이며 WCAG AA의 일괄 최소치로 표현하지 않는다. [W3C의 44px 강화 기준은 AAA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)다.

## 6. 권장 정보 구조와 화면

### 여행 단계에 맞는 시작점

| 단계 | 처음 보이는 정보 | 대표 행동 |
|---|---|---|
| 여행 전 | 큰 동선, 도시별 체류일, 아직 확인하지 않은 티켓/이동/숙소 | 계획 이어서 만들기 |
| 여행 중 | 여행 현지 날짜, 지금/다음 일정, 이동, 예약 시각, 저장 상태 | 길찾기·순간 기록 |
| 여행 후 | 사진 표지, 날짜별 경험, 여행에서 남긴 글과 실제 방문 | 추억 다시 보기·에세이 만들기 |
| 날짜 미정 | 가고 싶은 장소·경험·희망 계절 | 여행으로 구체화 |

기본 진입은 위 단계에 따라 달라지되 사용자는 탭을 자유롭게 바꿀 수 있다. 여행 전 ‘오늘’을 열면 **Day 1 미리보기**로 명확히 표시한다. 진행 중 여행의 현지 날짜와 과거 날짜 조회를 구분한다.

### 허브: 지금 여행과 평생 기록

- 상단은 `내 여행`과 검색, 새 여행, 더보기만 유지한다. 통계·버전·백업은 더보기에서 접근한다.
- 진행/예정 여행은 첫 카드에 기간·다음 준비/일정·대표 행동을 표시한다. v1.8.8의 우선 여행 선택을 그리드/목록에서 동일하게 사용한다.
- 지난 여행은 대표 사진과 짧은 기억 한 줄 중심으로 보여준다. 국가·도시·연도 필터는 필요할 때 펼친다.
- 예제 여행은 예제로 표시하고 내 여행으로 복사하게 한다. 첫 설치 안내가 여행 열기를 밀어내지 않게 한다.

### 여행 안의 헤더와 메뉴

헤더는 `뒤로 / 여행 이름 / 동행 또는 더보기` 한 줄, 아래 `Day 6 · 엘 찰텐 · 기기에 저장됨` 문맥 한 줄로 구성한다. 긴 제목은 헤더에서 축약하고 누르면 전체 이름을 확인한다. 통계·환율·회화는 더보기 또는 해당 상황의 도구로 이동한다.

최종 권장 하단 메뉴는 **오늘 · 일정 · 기록 · 지출**이다. 준비는 일정의 준비 영역과 출발 전 체크 카드에서 접근한다. 기존 5개 메뉴는 화면 연결과 사용자 적응을 확인하며 단계적으로 전환한다. 메뉴 이름·정보 위치·사진 표현을 한 번에 모두 바꾸지 않는다.

### 큰 계획/일정: 경로를 이해하고 일부만 바꾸기

`큰 동선 / 하루 일정 / 지도`를 하나의 보기 전환으로 제공한다. 큰 동선은 도시별 기간·숙소 기준·예약 고정 항목·다음 도시까지 이동을 요약한다. 도시 카드를 누르면 해당 구간의 일별 일정이 열린다. 기본 카드는 간결하게, 편집은 명시 버튼이나 더보기에서 접근한다.

AI 변경은 `이 일정 / 오늘 남은 일정 / 이 도시 구간` 범위를 먼저 보여준다. 변경 전후, 보존되는 예약·완료 일정·기록, 달라지는 날짜/이동을 확인한 뒤 적용한다. 실제 경로 서비스에서 확인한 이동 시간과 AI 추정값은 출처·확인 시각·추정 표시로 구분한다. 30분은 편집 시간 단위로 활용하되 긴 활동을 임의의 30분 카드들로 분해하지 않는다.

### 오늘: 현장에서 필요한 행동

첫 화면에 날짜 선택과 다음 일정, 예약 시각, 이동 정보를 배치한다. 기본 행동은 **길찾기 · 기록 · 완료**로 통일하고 편집·고정·삭제는 더보기로 둔다. 완료 버튼은 되돌릴 수 있어야 한다.

변수가 발생하면 `30분 늦었어요 / 비가 와요 / 쉬고 싶어요`처럼 이유를 선택해 남은 일정 RePlan으로 연결한다. 실행된 일정과 이미 남긴 기록은 그대로 유지한다. 완료한 일정은 접을 수 있고, 펼치면 실제 방문과 기록을 함께 볼 수 있다.

### 기록: 여러 순간과 하루 회고

`+ 순간 기록`은 날짜·시각·선택한 일정이 미리 들어간 짧은 입력창을 연다. 일정 연결 없이도 기록할 수 있다. 사진만/짧은 글/긴 글을 모두 허용하고 AI 다듬기는 글이 있는 경우 제공한다. 저장·실패·초안 상태를 분명히 표시한다.

기록 탭은 **선택한 날짜의 시간순 피드**와 전체 여행 탐색을 제공한다. 각 카드에는 글 첫 부분·대표 사진 하나·시각·장소·작성자를 표시한다. 사진은 예컨대 72×72px 썸네일로 카드 안에 고정하고, 열면 비율을 보존한 사진과 전체 글을 보여준다. 하루 회고는 순간들을 모아 쓰는 별도 문서다.

여행 후에는 표지→날짜별 경로와 경험→회고 흐름으로 읽는다. ‘순간 기록’이 기존 하루 글을 덮어쓰지 않아야 한다. 개인/동행 공개 범위는 기록마다 선택한다.

### 공유와 에세이

현재 사본 기능에는 파일 전달을 기본으로 유지하고 짧은 링크가 가능한 경우에만 링크를 제공한다. **동행 초대**는 같은 여행을 읽고 수정하는 별도 서비스로 구축한다. 공개 보기와 편집 권한, 링크 만료/취소, 변경 제안과 이력을 제공한다. 개인 일기는 기본 제외하며 받는 사람의 화면을 미리 볼 수 있어야 한다.

PDF/에세이는 날짜별로 `당일 계획 → 실제로 한 일 → 순간 글·사진 → 하루 회고`를 구성하고 지출은 부록으로 둔다. 예정/완료/건너뜀을 사실대로 표시하며 실제 방문 시각이 없으면 꾸며내지 않는다. 원문·AI 승인문 포함 여부를 선택하고, 에세이 초안에는 사용한 기록 ID를 연결한다. 블로그용 텍스트/Markdown 내보내기도 같은 이야기 모델을 사용한다.

## 7. 화면 개선을 지탱할 구조

프레임워크 전환보다 입력·저장·출력의 계약을 통일하는 작업이 우선이다. 다음 작은 모듈부터 기존 구조에 연결한다.

| 모듈/모델 | 책임과 연결 |
|---|---|
| TripAdapter | 기본 샘플·구버전·공유·AI 결과를 표준 title/cat/dayId/spotId/ISO 날짜로 변환. 변환 후 검증. 원본 보존과 이전 버전 구분 |
| Place / TripStageResolver / TripClock | 공백을 보존한 지명·식별자, 여행 단계, 여행 현지 날짜/시각을 모든 화면에서 공유 |
| JournalEntry | 독립 ID, tripId/dayId, 선택 activityId, 발생 시각, 원문/승인문, 작성자, 공개 범위. 순간과 하루 회고 구분 |
| MediaRepository | IndexedDB에 비율을 유지한 사진 Blob과 파생 썸네일 보관. 화면 JSON에는 mediaId만 참조. 백업·복원이 사진까지 포함 |
| ViewState | 여행/탭별 선택 날짜·보기 방식·지도 선택·스크롤. 상세 뒤로가기와 탭 전환 모두 복원 |
| TravelStoryBuilder / ExpenseSummary | 화면·PDF·블로그가 같은 날짜별 사실/기록과 비용 집계를 사용. 출력기에서 다시 다른 분류로 계산하지 않음 |
| CollaborationService | 회원/권한·초대 ID·엔터티 revision·변경 이력·충돌/오프라인 재전송. 사본 계약과 별도로 둠 |

기존 일정별 activityRecords와 하루 journals는 원문·사진·AI 승인 이력을 보존해 JournalEntry로 옮긴다. 과거 작성 시각이 없으면 미상으로 남기며 이전 시각을 작성 시각으로 채우지 않는다. 사진 크롭으로 이미 사라진 부분은 새 구조만으로 복구되지 않는다.

로컬 저장→백업→동기화의 상태를 구분한다. 현재 전체 여행 JSON/localStorage 저장은 기록이 쌓일수록 비용과 용량 부담이 커지는 구조이므로, 미디어 분리와 복원 검증이 ‘평생 다이어리’의 기반이다. 저장 성공을 확인한 뒤 UI 상태를 확정하는 기존 경계를 이어간다.

### 신록 규칙과 다음 설계의 정합성

신록의 16대 규칙과 배포 체크리스트도 확인했다. 일부는 초기 구현 수단을 고정하고 있어, 후속 구현 시 목적에 맞게 문서·검증 계약을 함께 갱신할 필요가 있다. 이번 검토에서는 아래 규칙을 변경하지 않았다.

| 기존 규칙 | 보존할 목적 | 다음 규칙의 권장 방향 |
|---|---|---|
| R-1: Zero-Backend, GitHub Pages 고정 | 낮은 비용과 통신이 없어도 쓸 수 있는 여행 앱 | 현재 운영은 이미 Vercel. 개인 기록/일정의 로컬 사용을 보장하고 서버 연결은 동행 협업·선택 백업에 사용. 실시간 공동편집을 제공하려면 Zero-Backend 범위 조정이 필요 |

## 8. 구현 묶음과 완료 조건

| 순서 | 작업 묶음 | 완료 조건 |
|---|---|---|
| A | **콘텐츠 신뢰성**: 샘플 계약, 도시명, 다음 일정 fallback, 날짜/분류 통일 | 기본 v14의 제목이 정상 표시되고 내보내기→가져오기 왕복 성공. 엘 칼라파테/엘 찰텐이 별도 지명으로 유지. 사용자 기록/완료 상태 보존 |

B의 추가 현장 확인은 Android Chrome/PWA와 iOS Safari에서 키보드·시스템 뒤로가기·하단 안전 영역·200% 확대를 포함한다. 이번 390px 브라우저 검토만으로 그 결과를 보증하지 않는다. 공동편집은 E의 서버·두 기기 검증이 끝난 뒤 제공 완료로 표시한다.

A와 B를 먼저 작은 릴리스로 적용한 뒤 기록 화면 개편을 진행하는 것이 적합하다. 이렇게 하면 기존 기능을 유지하면서도, 사용자는 더 정확한 일정과 편한 휴대폰 조작을 먼저 체감할 수 있다.
