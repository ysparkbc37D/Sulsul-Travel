# 개발 순서와 검증 계약

작성일 2026-09-08, 구현 갱신 2026-09-10. 최초 계획은 운영 코드 v1.2.9 기준이며, A와 B의 첫 사용 가능 단위를 v1.3.0에 반영했다. C~F와 서버 기반 공동편집은 아래 계약에 따라 후속 구현한다.

## 1. 구현 순서

| 단계 | 작업 | 핵심 파일/경계 | 완료 기준 |
| --- | --- | --- | --- |
| A: 변경 안전성 | 튜닝 fallback 직접 교체 제거; item ID 기반 RePlan Patch; 원본·예약·완료 보호 | `executeScheduleTuning`, `js/domain/replan.mjs`, repository | **v1.3.0 1차 완료**: 로컬·AI 모두 비교 승인, revision 검사, 완료·고정 보호. 동시 서버 revision은 D에서 확장 |
| B: 큰 계획/오늘 | PlanBlock 모델, 새 앱 셸, 기존 일정 어댑터, 오늘의 다음 행동 | `index.html`, 기존 `renderActiveTripWorkspace` | **v1.3.0 1차 완료**: 4개 메뉴, 거점 카드, 오늘 행동·완료·건너뜀·RePlan, 360px 검증 |
| C: 개인 기록과 보관 | Experience/Moment, 하루 확정, IDB·미디어·백업 이전 | storage/media + 기존 journal adapter | 사진 포함 백업 왕복, 이전 실패/중단 복구, 계획 삭제와 실제 기록 분리 |
| D: 공동 공간 | 로그인·초대·역할, 서버 트랜잭션, Outbox, 증분 동기화 | 새 server/sync 포트 | 다른 기기 3개에서 동시 수정·오프라인·권한 회수·재전송 검증 |
| E: 근거 기반 계획 | 실제 이동·운영·예약 출처, 제약 solver, 대안 비교 | evidence/routing/constraints | 실행 불가능한 일정은 확정 불가, 출처 없으면 미확인, 부분 채택 재검증 |
| F: 평생 회고 | 검색·연도별 여행장, 문단별 근거 있는 에세이, 내보내기 | library/records/story jobs | 미방문을 서술하지 않음, 타인 비공개 기록 제외, 편집본 재생성 보존 |

실사용 가능한 최소 단위는 A+B+C의 개인 여행 경험, 그리고 D가 결합된 공동 여행 경험이다. 동행자 뱃지만 먼저 붙인 상태를 공동편집 완료로 발표하지 않는다. E/F는 기능 플래그로 점진 활성화한다.

## 2. 작은 작업 단위

- **RP-01** RePlan Domain: 현재 계획+이벤트+제약 → 변경안. AI 또는 수동 제안 모두 같은 schema로 검증.
- **RP-02** 승인 적용: current revision 비교, opId 멱등, 완료 항목 보호, 단일 저장. 기존 ‘일정에 추가’와 ‘기존 일정 수정’ 경로 분리.
- **UX-01** 큰 계획 카드: 날짜·박수·거점·핵심 경험·숙소·이동·과제를 선택적으로 펼침. 기존 DOM ID 어댑터로 회귀를 제한.
- **UX-02** 오늘 화면: 다음 행동·RePlan·완료·순간 기록. 개발용 GPS 테스트를 실제 여행 화면 밖으로 옮김.
- **DATA-01** Sheet 가져오기: 원본 셀 좌표, 후보 필드, 날짜/도시/통화 충돌, 예전 계획 여부를 검토하고 새 초안 생성.
- **DATA-02** IDB 이전: 미디어 포함 복원 시험까지 통과한 뒤 전환.
- **COLLAB-01** 인증·권한: 관리자/조정자/참여자/열람자, 개인 기록 공개 범위, 초대 만료·회수.
- **COLLAB-02** 경합: 동일 일정 수정, 다른 일정 동시 수정 후 전체 제약 확인, 오프라인 작업 보존, 서버 ack 기준 상태.
- **STORY-01** 확정 기록만 에세이 입력: 문단별 source IDs, 원문·초안·사용자 편집본, 공동 글 사용 허가.

## 3. 검증 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 대만 날짜 불일치 가져오기 | 항공 기간과 숙소 날짜를 나란히 보여주며 자동 날짜 보정 없음 |
| 과거 시트의 다른 지역 교통 메모 | 현재 여행에 자동 병합하지 않고 사용자 선택 |
| 완료 관광 후 60분 지연 | 완료 항목/실제 기록 보존, 이후 미완료만 재계획 |
| 고정 18시 예약과 지연 충돌 | 예약 자동 이동 없음, 충돌한 선택 일정/대안 표시 |
| 23:40 출발→다음 날 도착 | 날짜와 지역 시간대 보존, 시각 문자열 정렬로 역전되지 않음 |
| RePlan 생성 중 동행자 수정 | 적용 시 충돌 UI, 타인 수정 유지 |
| 같은 승인 두 번 또는 네트워크 재전송 | 서버 작업 ID로 한 번만 반영 |
| 참여자/열람자가 적용 API 호출 | 서버 권한 검사로 거부; UI 숨김만으로 처리하지 않음 |
| 기기 A 오프라인, B 온라인 변경 | A의 원문 보존, 재접속 시 변경안 재비교 |
| 사진 업로드 실패/쿼터 초과 | 텍스트 저장 상태와 사진 실패 분리, 성공 오표시 없음 |
| 계획에만 있고 방문하지 않은 장소 | 에세이의 방문 사실로 생성하지 않음 |
| 하루 확정 뒤 수정 | 새 확정 버전과 이력, 과거 에세이 근거 버전 보존 |
| 다른 앱 캐시 공존 | 술술트래블 캐시만 갱신/정리 |

## 4. 완료 정의와 운영

기획자는 사용자 과업·상태·문구, 아키텍처 담당은 모델·트랜잭션·권한, 구현자는 작은 기능, 검증자는 실패·경합·복원 증거, 통합 담당은 버전·캐시·롤백을 책임진다. 역할은 작업 분리 기준이며 여러 에이전트의 자동 병렬 실행을 뜻하지 않는다.

각 작업은 계약 → 익명 fixture → 최소 구현 → 실패/회귀 검증 → 실제 브라우저 → 변경 설명 순서다. 공용 `index.html` 편집은 통합 담당 한 명이 수행한다. 서버 도입 전 운영 주체·리전·예산·인증 방식을 확인하되 A~C의 독립 작업을 막지 않는다.

플래너 품질은 ‘방문 수’ 외에 hard constraint 위반 수, 근거 누락, 사용자 수정률, 제안 채택률, p95 지연·비용으로 측정한다. 개인정보 원문은 품질 로그에 수집하지 않는다. 초기 사용자 테스트는 과업 중심 5~7명으로 실시하며 목표 시간은 제품 명세에 기록한다.

## 5. 시안 검증 범위

시안은 `design/travel-companion.html`에 독립되어 있다. 외부 API·운영 저장소와 연결되지 않는다. 화면 전환, 거점 선택, 세부 수정, 지연/비/휴식 대안, 제안/확정, 되돌리기, 한 줄 기록, 하루 확정, 에세이 편집 흐름을 확인한다. 자동화 결과와 실제 관찰은 [시안 검증 기록](prototype-checks.md)에 남긴다.
